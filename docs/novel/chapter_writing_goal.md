# 目标：重做「章节撰写」

日期：2026-11-25。这是交给执行者（新的会话或智能体）的目标说明，按三个阶段做：先调研出方案、等作者确认，再重建，最后做质量检查。现状和同类项目的做法已经查过一遍，写在下面，动手前抽查核实即可，不必从头再查。

## 一句话目标

在不丢掉现有质量保护的前提下，把「章节撰写」重做成：每一章、每一场要带的材料由代码按规则挑；写作和检查的步骤固定，每章调用次数有上限；检查结论都带原文出处，能定向修好；章节验收后自动留下前情，供后面的章节使用。目标是标准档每章的调用次数从现在的约 25–30 次（最多时一章评审记录 79 份）降到一个可预期的上限，而成稿质量不降。

## 一、现状（已核实）

**流程。** 点「撰写下一章」后，一章依次经过：

1. 整理全书设定（全书设定变了才做，1 次调用）。
2. 读本章契约。契约由场景规划阶段写出，缺了或不合格就退回场景规划。
3. 规划评审：评本章场景规划，不过就让模型改规划，最多 2 轮。
4. 逐场写作：每场写完都评一次，不过就重修，最多 2 轮，可以走多轮对话。
5. 整章评审：契约合规、读者盲读、现实合理性三份模型评审，加一份不花调用的衔接检查，合在一起判。
6. 定向重修：按问题引用的原文找到所在的场，只改那几场；判定问题出在规划里时，回去改规划、整章重写，最多 1 次。
7. 验收入账：提取本章的事实变化，和账本核对；有冲突时再问模型裁定；通过后写入正式章节和账本。
8. 被拦下的章节进「待复审」，作者可以照建议重修、重跑评审、人工放行或回去改规划。

**规模。** 相关代码约 1.5 万行，见文末「代码位置」。

**成本。** 开发日志里的实测：同样三章 73–91 次调用、25–27 分钟。样例副本 23 章的评审记录每章 4–79 份，第 15、16、20 章分别是 50、40、79 份；第 18–22 章出现过「契约改了、整章作废重写」。花费的长尾没有上限。

**给模型的材料。**

- 写场景的设定材料已经改成按本场挑（提交 f85351a）：名称与规则登记表、本场人物的卡、相关势力、世界观正文、本场人物的背景。
- 章节契约仍然整份发给写作和评审：写成英文字段名的原始数据，按字数截在 8000–10000 字。
- 评审还会收到全书设定和账本的原始数据，各截在 7000 字左右。这几处都违反下面的材料组合原则。
- 前情只有上一场或上一章的结尾 2500 字。没有更早章节的摘要，也不检索已经写好的正文。

**质量判定。**

- 每个维度打 1–5 分，平均分过门槛才算过；门槛按题材档案定。
- 场次越界（写第 N 场时把后面几场的事提前写了）大约每三章一次。每次都被闸门抓住，代价是多一轮重修。
- 评审每一轮都会换个说法提同一个问题，所以现在靠「同一句引文反复被引用」来判断已经修不动。

**已知没接上或用不到的部分。** 叙事图里有四条检查没有任何数据来源（见开发日志 2026-09-10）。契约里不少字段只在校验里有意义，写作时用不上。

**界面。**

- 章节撰写页：「撰写下一章」「撰写全部剩余章节」「重写本章」「分析章节」「停止」，以及质量闭环档位「关闭 / 标准 / 严格」。状态栏显示「第 N 章 · 场景 i/j」。
- 待复审：「照建议重修」「重跑评审」「人工放行」「回去改规划」。

## 二、同类项目的做法（已查，动手前抽查原文核实）

- **InkOS**（github.com/Narcooo/inkos，2.0 开发版）
  - 每章依次是 规划 → 组装上下文 → 写 → 结算状态 → 观察 → 提交。
  - 上下文由专门的一步从结构化状态里按任务挑选，分「受保护」和「可压缩」两层，不整份塞文件。每章留下实际选了什么、为什么选的记录。
  - 故事状态存成带校验的结构化文件，另外生成给人看的文字版。
  - 结算这一步提交带原文证据的增量，由程序校验后和正文一起原子提交。
  - 评审只给观察意见，不把章节判成通过或不通过；修订是单独、明确的动作。
  - AI 腔检查只出意见，去 AI 味要专门触发。字数目标换算成一个区间，超了也不截断。
  - 检索的做法：先用关键词召回候选，再让模型挑。
- **ainovel-cli**（github.com/voocel/ainovel-cli）
  - 由确定性的程序调度，写手按固定顺序做：取上下文 → 读前一章 → 规划 → 起草 → 一致性检查 → 提交，提交时写入事实。
  - 上下文按篇幅换策略：全文、滑动窗口，或者章、弧、卷三层摘要。按伏笔、人物出场、状态变化推荐相关章节；预算按模型的上下文长度算。
  - 编辑只在弧和卷的边界做审阅。可以设成每章停下来等人看。
- **autonovel**（github.com/NousResearch/autonovel）
  - 用正则查套语，再用模型打分，低于分数线就重写；修订到分数不再上升就停。
  - 设定分层存放：大纲、人物、世界、硬事实、文风。改了一层会记一笔，提醒别的层要跟着改。
- **AI_NovelGenerator**（github.com/YILING0013/AI_NovelGenerator）：分层规划到章节计划，按计划写，作者看过候选再保存。
- **论文**
  - Re3：写之前注入计划和故事状态，写完按连贯性重排，再按长程事实修改。
  - DOC：细纲控制让长篇连贯性明显提高。
  - Agents' Room：分工写作，共用一份草稿。

**对我们有用的几条：**

1. 材料由代码挑，每章留一份「带了什么、没带什么」的记录。
2. 故事状态以结构化文件为准，验收时用带证据的增量更新，和正文一起提交。
3. 前情用分层摘要（最近几章的摘要，加更早部分的概要），再按本章人物和线索挑相关章节。只有要找已写正文里的某段原文时才用检索。
4. 代码能判的检查全交给代码，不花调用；模型只判代码判不了的，而且必须附原文引文。
5. 调用次数要有上限，不靠无限重修；修不好的交给作者，我们已有「待复审」。

## 三、目标设计（建议；第一阶段调研后可以调整，改动写明理由）

**1. 每章的固定步骤和调用预算**（以 3 场的章节为例，标准档）

| 步骤 | 做什么 | 调用 |
|---|---|---|
| 备料 | 代码挑出本章和每一场的材料，记下带了什么、没带什么 | 0 |
| 写 | 逐场写 | 每场 1 |
| 代码检查 | 衔接、字数区间、套语和 AI 腔高频词、登记表外冒出的新名字、时间读数、外文编号等 | 0 |
| 整章检查 | 一次评审，同时看设定、契约、越界、衔接和合理性；每条问题必须附正文原文，分「硬伤」和「建议」 | 1 |
| 定向重修 | 只重写有硬伤的场，最多 1 轮，再复查 1 次；复查时先由代码看被引的原文还在不在 | 0–4 |
| 验收 | 一次调用同时提取本章事实变化和本章摘要，程序校验后和正文一起提交 | 1 |

常见情况每章 5 次调用，最多 9 次；场数不同按比例算。严格档可以把整章检查拆成两份独立评审，重修放到 2 轮。关闭档只写和验收。规划的质量归场景规划阶段管：章节撰写只用代码检查契约是否齐全，发现规划本身有问题就走「回去改规划」。

**2. 材料**（遵守下面的组合原则）

- 写一场：沿用已做好的本场设定材料，另加这些块：
  - 本章契约里属于本场为止的部分，写成中文条目。
  - 前情：最近两三章的摘要，加本场人物最近一次出场时的状态。
  - 上一场或上一章的结尾。
  - 下一场的标题，以及后面场次的禁区。
- 整章检查：本章正文、本章契约（中文条目）、名称与规则登记表、本章出场人物的卡、和本章有关的未了结线索、前情摘要。不再发截断的全书设定和账本原始数据。
- 每章存一份材料记录：每块的名字、字数、是否带上。界面上能看到（例如放在「分析章节」里），作者不用翻文件。

**3. 前情记忆**

- 每章验收时写一份本章摘要（和事实提取同一次调用），再更新人物当前状态和线索表。
- 写后面的章节时，由代码按出场人物和契约点到的线索挑选。
- 篇幅大了用分层摘要：每一幕或每 N 章合成一份概要。
- 是否检索已写正文，第一阶段评估后再定：先试结构化挑选加关键词检索，实测不够再考虑向量检索。

**4. 检查和重修**

- 硬伤的种类沿用题材档案里的硬伤代码。
- 「有没有修好」尽量由代码判：被引的原文是否还在、确定性检查是否还报同样的问题。
- 修不好就进「待复审」，不再追加重修轮次。

**5. 契约和叙事图**

- 章节撰写只读契约，不改它的文件格式。逐个字段写清楚谁在用、怎么用；没人用的字段不再发给模型，文件里照旧保留。
- 叙事图里没有数据来源的检查，要么接上，要么删掉，并写明理由。

**6. 界面**

- 按钮、状态栏和待复审流程保持不变。
- 每章用了几次调用、在哪一步被拦，写进章节列表或右栏，作者一眼能看到。

## 四、需要作者拍板的决定（第一阶段结束时一起问，问完再动手）

1. 是否取消「平均分过门槛才放行」，改成「没有硬伤就通过，建议项只记录、可以一键照建议润色」？
2. 标准档每章调用的上限定多少？（建议：场数 + 4）
3. 逐场评审是保留（越界现在主要靠它抓），还是合并成整章一次？
4. 已写正文的检索：先不做、做关键词检索，还是直接上向量检索？
5. 叙事图里用不到的部分：删，还是接上数据来源？
6. 旧作品里已经验收的章节，要不要补写摘要？补写会花调用，每章 1 次。

## 五、硬性约束

- 旧作品打开不报错。任何改动都不删除作者已有的产物和手动修改：已验收章节、账本、待复审记录、旧格式契约都要照常读得出来。
- 小说代码不引用短视频代码。
- 提示词是正常中文，不额外要求模型「只写中文」。字段名、编号和固定取值可以是英文，因为程序靠它们读回结果。
- 材料组合六条原则：
  1. 每一次调用先列清楚要带哪几块。
  2. 按结构和编号挑，不按文件路径、不按相似度挑。
  3. 每块有中文名和用法（必须遵守 / 参考），按重要性排。
  4. 每块有篇幅预算；超了从最不重要的一块起整块去掉，并写明去掉了什么，不在一块中间截断。
  5. 结构化数据写成中文条目，只有需要模型照抄字段时才给原始数据。
  6. 要不要重做，按原始数据的指纹判断，不按拼出来的文字判断。

  已有的公用代码可以直接用（材料按块取舍、本场设定材料）。
- 会花模型调用的实跑，先说清楚要跑几次、大约多少次调用，得到同意再跑。
- 样例作品先复制一份再动，原件只读。
- 在当前分支提交，不推送；不要把别人改过的短视频文件带进提交。
- 向作者汇报时用界面上的按钮文案和界面行为来讲，不贴函数名。每个阶段结束时说清楚：做了什么、实测数字、哪些没做、为什么没做。

## 六、三个阶段

**阶段一：调研和方案。** 不改代码，不调模型。

1. 读现有的章节撰写代码、四份小说文档，以及开发日志 2026-09-06 到 09-10 的记录（那里写着每一道保护是为了解决什么问题加上的）。
2. 抽查上面列的同类项目原文。
3. 从样例副本已有的评审记录里统计：每章调用次数的分布、哪一步最贵、哪些问题最常见。只读记录，不新跑。
4. 写出《章节撰写重构方案》，内容包括：
   - 新流程图和每步的调用预算。
   - 每一块材料的来源和预算。
   - 保留、删除、新增的清单。现有的每一道保护都要说明在新流程里由谁接手，或者为什么可以去掉。
   - 旧作品怎么兼容。
   - 风险，以及第四节那几个决定的建议答案。
5. 停下，等作者确认。

**阶段二：重建。**

- 按确认的方案分步实现，每一步都能单独测试。
- 先搭新流程，接到现有的按钮和待复审流程上；新流程跑稳以后，再删掉被替代的旧代码。
- 每删一块都说明它原来防的是什么，现在由谁防。
- 新代码每次有改动，都同时写清楚「产品里谁会调用它」，避免写好了却没接上。

**阶段三：质量检查。**

- 单元测试：材料挑选、调用预算上限、硬伤判定、修没修好的判断、前情摘要的读写、旧作品兼容。
- 跑 `pytest tests/novel tests/common` 和全量测试。全量里短视频镜头页那一项是改造前就失败的，照实写。
- 不花调用的核对：在副本上把某一章每一步的材料拼出来，看都带了哪些块、多少字、去掉了什么。
- 实跑对比（先报次数，得到同意再跑）：在副本上用新流程连写三章，和开发日志里同类三章的基线比较这些数字：
  - 每章调用次数（平均和最多）
  - 用时
  - 一次就验收的章数、待复审数、人工放行数
  - 越界次数
  - 相邻章开头的套语
  - 硬伤数
- 质量不降的判断：请作者盲读同一章的新旧两稿。如果要让模型做两两比较，要另外花调用，先问。
- 更新架构、接口、交互、开发四份文档和开发日志，写明验证结果，然后提交。
