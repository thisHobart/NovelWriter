# 目标模式提示词：持续完善「场景规划」

日期：2026-11-25。

这里说的「章节规划」指步骤栏里的「场景规划」这一步：「生成章节大纲」「规划场景」两个按钮，产出各幕的章节大纲、逐章场景规划和章节契约；短篇的「规划场景」也算在内。
「章节撰写」页不在范围内，它另有[目标提示词](chapter_writing_goal.md)。两边的交界（写章节时的规划评审、退回规划修改）只记下影响，不改。

## 怎么用

1. 在本仓库、`novel-module-rework` 分支上新开一个 Claude Code 会话。想让它无人值守地跑，就切到自动模式，否则每个工具调用都要你点允许。
2. 把下面「/goal 条件」那一整段复制进去发送。
3. 运行中输入 `/goal` 可以看进度，输入 `/goal clear` 停止。
4. 跑完后看本文件第八节（待作者拍板、建议的实跑）和第九节（进度记录）。

判断「完成没有」的是另一个小模型，它只看对话记录，不读文件、不跑命令。所以条件里要求每轮把证据贴进对话。

## /goal 条件（整段复制，不到 4000 字）

```text
/goal 按 docs/novel/chapter_planning_goal.md 持续完善「场景规划」这一步（生成章节大纲、规划场景、章节契约）。每一轮先读这个文件，从第三节挑排在最前、还没完成、也不依赖作者决定的一条，照第五节的做法改完，跑第六节的测试和不花调用的规划检查，在第九节「进度记录」追加一行（改了什么、检查数字的前后对比），把这一条标成「完成」，然后提交到当前分支（不推送，不暂存那四个短视频文件）。每轮结束时在对话里写明「第 N 轮」，并贴出：这一条的完成标准逐项对照、测试汇总行、检查脚本输出。
硬性规则：不调用模型，也不跑任何会花模型调用的脚本或界面操作，需要实跑的写进第八节「建议的实跑」并写明次数；旧作品打开不报错，章节契约的字段名和文件格式不变；不删除作者已有的产物和手动修改；小说代码不引用短视频代码；提示词用正常中文，不加「只写中文」之类的要求；需要作者决定的事不做，写进第八节「待作者拍板」后接着做下一条；同一条连续两轮做不成，标成「卡住」并写明原因，接着做下一条。
完成条件，满足任一即可：A. 第三节每一条都标了「完成」「卡住」或「待作者拍板」，并且最后一轮在对话里贴出：小说与公共测试全部通过、全量测试只有已知的短视频那一项失败、ruff 没有报错、规划检查脚本对工作副本的输出不比第二节的基线差、这次运行改过的文件都已提交；B. 剩下的每一条都依赖第八节里的作者决定，并且已经在对话里列出这些决定；C. 已经进行到第 40 轮。
```

## 一、范围

改的是「场景规划」页两个按钮背后的流程：发给模型的材料、对规划结果的代码检查、出了问题怎么退回重写。界面按钮和页面交互不变。

不改：章节契约的字段名和文件格式（写章节那边按它读，旧作品也按它存）；「章节撰写」页的流程；世界设定、故事结构两个阶段。

## 二、现状（已查过，执行时抽查核实即可）

### 流程

- **生成章节大纲**：每一幕一次调用（六幕就是 6 次）。带作品参数、这一幕的故事结构和地点要求，不带名称登记表和人物名单，却要求模型「列出本章涉及的人物、势力和具体地点」。代码查章标题和世界观冲突，然后由模型做一次大纲评审，按平均分放行。没过就把原稿和问题交回去重写，最多重试 2 次。已有可用大纲的幕跳过。
- **规划场景**：每章一次调用，带：
  - 作品参数；
  - 这一幕全部章的大纲；
  - 整份世界设定；
  - 契约格式说明，含仍未了结的悬念、后面章节的依赖，以及既有事实、时间事件的原始数据（按字数截断）；
  - 上一章结尾 2000 字。
- **规划场景的代码检查**：契约格式、编号撞车（新事实可能和已有事实是同一件时，会再调一次模型判断）、跨章引用、叙事图、世界观冲突。没过就把原稿和问题清单交回去重写，最多重试 2 次，问题没变化就提前停。全部章规划完再做一次跨章检查，点到哪章就重写哪章。
- **跳过规则**：已有可用规划的章跳过；已经验收的章，规划不再重新生成。
- **短篇**：一次规划 3–6 场，契约检查是同一套。
- **质量评审**：规划阶段本身不评审场景规划的质量，写章节时每章先做一次「规划评审」。

### 实测问题（样例副本，`current_work` 的复制件，30 章）

1. **场景边界基本没起作用。** 写一场戏时，系统把后面场次的「场景边界」列成「禁止触碰」，靠它防止模型提前写掉后面的事。但规划提示词里这一栏只给了一个空数组 `"scene_boundaries": []`，一个字都没说该写什么。
   - 81 条边界里，53 条是「scene_1: 地点」这样的一行字。
   - 另外 28 条是模型自己编的格式，一共 7 种（start/end、end_action、end_line、location/purpose……）。
   - 写第 1 场时本该拦住 51 条后面场次的边界，实际只有 31 条进了提示词。场次写在 `scene_index` 里、或者写成纯数字的那 20 条认不出来，直接丢了。
   - 进了提示词的那些，大多只写了地点，没写这一场停在哪里。写章节时的规划评审修复格式里倒有 must_do / must_not_do / end_state，可规划阶段从没要求过这几项。
2. **提示词自相矛盾。** 「后续章节依赖本章」那一段，把第 1 章就埋下的悬念、引入的事实也写成「本章必须埋下」「本章必须引入」，而同一份提示词前面要求「id 不能与任何既有悬念重复」。检查本身没错（已经埋下的不算漏），错的是提示词的说法。另外还有空名字「事实 F-003-02（）」：后面章节引用它时没写名字，提示词也没去取引入它那一章写的名字。
3. **材料不合下面第四节的六条原则。**
   - 整份世界设定、整幕大纲每章都带。
   - 既有事实和时间事件按英文字段名的原始数据发过去，按字数截掉一部分：第 12 章那份截掉了 6 条事实、7 条时间事件、1 条已了结的悬念，还留着 `_context_meta`、`truncated` 这类内部字段。
   - 大纲那一步反过来，什么设定都不带。
   - 规划提示词字数 7340–14691，中位数 12987。这是 `current_work` 里存下的 76 份旧提示词，当时世界观一块只有两千来字。用现在的代码重新拼（检查脚本），世界观一块带的是整份世界设定，28335 字，总字数 35321 / 44292 / 46063。
4. **重来的次数。**
   - 30 章存了 76 份规划提示词，含开发期间的多次重跑和写章节时退回重规划。第 11–13、16–18 章各 5 份。
   - 第一次就被检查打回的 4 稿里，3 稿是「世界观未定义的内容：跃迁 / 全息」，1 稿缺章节契约。
   - 写章节时的规划评审一共 65 次，62 次通过；3 次没过，开出的硬伤都是「与真相矛盾」。
   - 第 18–22 章各有一份因为契约变了而作废的正文。
5. **场景数。** 长篇前 10 章每章 2 场，后面 3 场，有一章 4 场，没有上下限检查。短篇有 3–6 场的限制。

## 三、要改的事（按顺序做，每条有完成标准）

**0. 不花调用的规划检查。** 后面每一条都用它量。——**完成**（第 1 轮）

- 先把「生成章节大纲」「规划场景」拼提示词的部分抽成不调模型的函数，正式流程和检查脚本用同一个。
- 再写 `tools/check_planning.py <作品目录>`：读已有的大纲、规划和契约，拼出每章会收到的提示词（不发送），报告：
  - 每章场景数；
  - 场景边界：条数、能认出场次的条数、写了「停在哪里」的条数、写第 N 场时应拦和实际拦的条数；
  - 提示词：每章字数、每块字数、被截断的块、内部字段、「必须埋下 / 引入」里早已存在的条目、名字为空的条目；
  - 点到名字、登记表里却没有的人名和地名（借用写场景材料的认名办法）；
  - 跨章检查的结果。
- 完成标准：
  - 对工作副本跑出基线，填进第二节；
  - 测试里把发送函数换成一调用就报错的假函数，证明脚本不调模型；
  - 脚本只读作品目录，跑完目录里每个文件的修改时间不变。

**1. 场景边界写清楚，写场景时读得到。**——**完成**（第 2 轮）

- 规划提示词用中文说明每条边界写什么，字段名保持英文：`{"scene_number": 1, "must_do": [...], "must_not_do": [...], "end_state": "这一场停在哪里"}`。
- 代码检查：每一场都有一条带 `scene_number` 和非空 `end_state` 的边界。不合格的和其他契约问题一起退回重写。
- 读边界时认得旧作品已有的各种写法：`scene_index`、`scene`、纯数字、「scene_2: …」这样的文字。旧契约文件不改。
- 完成标准：
  - 检查脚本里「写第 1 场时应拦 / 实际拦」，对旧契约从 51 / 31 提高到 51 / 51；
  - 用假模型回复的单元测试证明新规划的边界都带 `end_state`；
  - 工作副本的契约文件一个字节都没变。

**2. 修掉提示词里的矛盾和空名字。**——**完成**（第 3 轮）

- 「后续章节依赖本章」按出处分开写：本章该埋下、该引入的，写「本章必须埋下 / 引入」；更早章节已经埋下的，写「第 X 章已埋下，第 Y 章要了结，本章不能了结它，也不能把它写没」。
- 名字为空时，取引入它那一章的名字。
- 完成标准：检查脚本里这两项都是 0；有单元测试覆盖「第 1 章埋下、第 14 章了结、重规划第 12 章」。

**3. 「规划场景」的材料按原则重排。**——**完成**（第 4 轮）

- 用 `prompt_material.fit_blocks` 拼材料，按下面的顺序排块：
  1. 本章大纲（必须遵守）；
  2. 名称与规则登记表（必须遵守）；
  3. 本章大纲点名人物的卡片（必须遵守，挑人办法和写场景材料一样）；
  4. 相关势力；
  5. 上一章结束时的状态（最后一个时间事件、结尾片段）；
  6. 仍未了结的悬念和后续章节依赖（写成中文条目，带编号方便照抄）；
  7. 既有事实和时间事件，按编号和人物、地点名挑，写成「F-001-01｜事实｜取值」这样的条目；
  8. 前后相邻两章的大纲（参考，用来划清本章到哪为止）；
  9. 世界观正文（参考）。
- 超出篇幅时从最后一块起整块去掉，并在材料末尾列出去掉了什么。不再出现截断和内部字段。英文字段名只留在要求模型输出的契约格式里。
- 完成标准：
  - 检查脚本里没有被截断的块，也没有内部字段；
  - 大纲点名的人物都带上了卡片；
  - 带了哪些块、去掉了哪些块记进运行记录；
  - 字数中位数不高于基线，高了要写明为什么；
  - 作品没有设定文件时照旧可用。

**4. 「生成章节大纲」补上该有的设定。**——**完成**（第 5 轮；登记表外人名的下降要重新生成大纲才量得到，见第八节）

- 先用检查脚本量「大纲点到、登记表里没有的人名和地名」。基线是 0 就在进度记录里写一行，跳过这一条。
- 不是 0 就补上名称与规则登记表、人物和势力名单（名字、身份），以及上一幕最后一章的大纲。同样用 `fit_blocks`。
- 完成标准：提示词里有这几块；有单元测试；检查数字下降。

**5. 补齐规划阶段不花调用的检查。**

- 长篇每章场景数的上下限：照基线先定一个范围，写进第八节，等作者确认后再改成打回。
- 规划里出现、登记表里没有的人名和地名：先只计数、写进日志，不打回。误报看清楚以后，再把要不要打回写进第八节。
- 完成标准：检查脚本和正式流程用的是同一套判断；有单元测试。

**6. 世界观冲突检查的说法和误报。**

- 打回的话写着「科幻内容」，不管作品是什么题材。改成按题材说。
- 回头看那 3 稿里的「跃迁」「全息」是真违背还是误报。误报就修，同时补测试。
- 完成标准：进度记录里写明结论；说法不再写死题材。

每一条做完，都同步改 `docs/novel/` 下相关的文档（架构、接口、开发），并在 `DEVLOG.md` 顶部加一条。

## 四、硬性约束

- 旧作品打开不报错。任何改动都不删除作者已有的产物和手动修改。章节契约的字段名、文件格式不变。
- 小说代码不引用短视频代码。
- 下面四个文件是别人改的，不暂存、不提交：
  - `core/short_video/v2/scail_dual_scene.py`
  - `core/short_video/v2/workflows/scail2_dual_scene.json`
  - `tests/short_video/test_comfyui_video.py`
  - `tests/short_video/test_dual_scene_ui.py`
- 只在当前分支提交，不推送。
- 不调用模型。会花模型调用的实跑一律不做，写进第八节，写明次数。
- `current_work` 只读。要用就先复制到草稿目录，在副本上跑。
- 提示词用正常中文，不要求模型「只写中文」。小标题用中文名，不用文件路径。字段名、编号和固定取值保持英文。
- 对话里的汇报用界面上的按钮文案和界面行为来讲，不贴函数名；代码位置写在进度记录里。
- 给模型的材料遵守下面六条原则：
  1. 每次调用列出要带哪几块。
  2. 按结构和编号挑，不按文件路径，也不按相似度。
  3. 每块有中文名和效力（必须遵守 / 参考），按重要性排。
  4. 每块有篇幅；超出时从最不重要的一块起整块去掉，列出去掉了什么，不在一块中间按字数截。
  5. 结构化数据写成中文条目；只有需要模型照抄字段时才给原始数据。
  6. 要不要重做按原始数据的指纹判断，不按拼好的文字判断。

## 五、每一轮怎么做

1. 读本文件，确认要做哪一条，再看第九节上一轮停在哪里。
2. 先读相关代码和测试，核实第二节对这一条的描述。描述不对就先改第二节。
3. 先写测试，再改代码。测试里的模型回复一律是写死的假回复。
4. 跑第六节的检查，数字写进第二节「当前」一栏和第九节。
5. 改文档和 DEVLOG。
6. 提交：只暂存这一条改过的文件和本文件。提交说明用英文、`fix(novel): …` 这样的格式，末尾带署名行。
7. 在对话里贴出：「第 N 轮」、完成标准逐项对照、测试汇总行、检查脚本输出。
