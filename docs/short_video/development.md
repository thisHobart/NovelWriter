## ComfyUI 固定多工作流（2026-11-15）

依据已确认的[方案](comfyui_workflow_plan.md)，在现有媒体服务上实现 API JSON 粘贴、命名、多工作流保存与选择，及参考图 1～N／首尾帧对应输入。生成仍通过内置 MCP 桥接，不接入文字 Agent Loop。

| 文件 | 当前职责 |
|---|---|
| media_workflows.py | 项目工作流列表、旧配置读取、API JSON 依赖裁剪、两类 H3 模板、图片与类型参数映射 |
| media_service.py | 冻结工作流标识、全部图片与参数；逐图上传、绑定 JSON 副本、单次提交与任务恢复 |
| media_repository.py、comfy_mcp.py | 复用图片导入、原子保存、上传／提交／查询／下载，不增加中间生图功能 |
| comfy_settings.py | 地址、工作流选择、新增、名称与 JSON 粘贴、后台校验与保存 |
| media_preview.py、workbench.py | 工作流切换、按模板生成图片／参数控件、刷新配置、生成与本地播放 |
| workflows/、NovelWriter.spec | 打包参考图及新增首尾帧两份固定 API JSON |
| tests/test_comfyui_video.py | UI→后端→MCP→ComfyUI 的图片／参数、配置与任务恢复回归 |

原参考图 JSON 保留用户原始模型和默认值，孤立的 LoadImage 不作为输入；实际有效输入为 137。更新 JSON 连入更多参考图后，UI 按对应输入显示。新增 minimax_h3_first_last.json 依据本地 MiniMaxH3ImageToVideo 节点，137／139 分别连接 first_frame／last_frame，使用 minimax_h3_fl2va_pruned_int8_convrot.safetensors，不沿用参考图 LoRA。

公开参数包括模板中的时长、种子、像素量、采样步数及参考图加速开关；不单独修改帧率，保留时长计算与模型网格关系。后端只修改本轮 JSON 副本。任务快照保留 workflow_id／name、各输入图片与参数，查询历史任务继续使用原始快照。

旧单工作流路径读取后转换为 JSON 快照，原 image_workflow 值保留但不执行、不显示；旧单图任务仍可查询取回。后续资产生图完成文件仍通过 MediaRepository.import_image(path, source=...) 进入媒体库，本轮不提前实现生图。

### 开发验证

19 项专项覆盖粘贴新增与更新、保存重开、三图变四图、首尾帧角色、全部图片分别上传、类型参数、大整数种子、原配置不被生成修改、任务刷新、跨工作流结果隔离、提交丢失对账与下载恢复。全量 **237 passed（14.96 秒）**；相关短视频代码 Ruff 检查及格式、依赖、Markdown 链接与差异检查通过。

通过真实 UI 控件提交本地 ComfyUI 0.44.2，三次均成功生成、保存 MP4，Qt 各解码 20 帧、读取 5166 ms，未出现播放错误：

| 链路 | 测试参数 | 耗时 |
|---|---|---|
| 原参考图模板 | 1 张输入、5 秒、0.1 百万像素、4 步加速 | 65.48 秒 |
| 新首尾帧模板 | 不同首尾图片、5 秒、0.1 百万像素、8 步常规采样 | 19.89 秒 |
| 粘贴的四参考图模板 | 4 个有效图片输入、5 秒、0.1 百万像素、4 步加速 | 195.56 秒 |

实际产物均为 480×224、24 fps、约 5.17 秒，含音频。测试仅覆盖这些参数的数据链路，不保证所有画面效果。测试配置、命令快照、任务记录、视频和 UI 截图独立保存在 quality_runs/comfyui_multi_20261115/，不修改用户项目及默认参数。未构建新的桌面安装包。

四图实测发现并修复了预检把模板旧图片名与服务器现有文件列表比较的问题：LoadImage.image 会在上传后替换，预检只跳过这个临时文件枚举；模型等枚举照常校验。

历史 2026-11-14 单图验证：用户风雪图片生成 992×416、24 fps、124 帧的 MP4，约 341 秒；Qt 解码正常。当时 13 项专项与全量 231 项通过，只代表当日实现。

## 镜头提示词缺失时的展示（2026-11-11）

当前全量 **151 passed（10.22 秒）**。已核对实际项目的离线界面显示；未请求模型补齐缺失资产，未改用户项目内容。

清理后全量 **151 passed（10.42 秒）**。额外离线集成验证当前镜头优化、未选镜头不变与资产引用保留；现有项目 80 条记录读取正常、清单不变。语法、文档引用和差异检查通过；未调用真实模型。

- `storyboard_skill.load_storyboard_skill` 读取 [SKILL.md](../../core/short_video/v2/skills/short-video-storyboard/SKILL.md)，在 storyboard 的 prepare 阶段追加到 instruction；requirements 与 prompt 冻结同一份 Skill，后续检查和重试不重新读文件。只在分镜生成时加载，不向普通聊天或资产阶段注入。打包配置包含该资源；文件缺失直接暴露读取错误，不静默降级为旧提示词。

- `review.py` 的 `check_candidate` 接收阶段要求、必要上下文与当前候选，复用现有规则和检查响应校验，返回 `QualityCheckResult(passed,feedback)`。它不触发生成，不保存报告。重试输入保留原始任务、上下文并加入最新候选与反馈。

- 资产审阅对照基础设定检查整组视图，分类型检查人物朝向、场景布局和道具可见表面，反馈包含具体路径、矛盾及建议。只检查文字，不声称验证了图片；反馈修订继续使用原有质量重试流程。
- 反馈、问题及检查原文只在本轮内存中使用，不保存检查报告或持久化 issues。已删除无调用方的独立检查服务与人工确认、报告写入接口。阶段 calls 仅记调用类型、错误类型和时间，调用计数回调不传原文。初始命令仍保存任务上下文；聊天和分段调用有独立的原文记录，不能套用阶段 calls 的限制。
- `creation.py` 接通目录／分镜与人物、场景、道具提示词；`batches.py` 的最终合稿复用相同 Agent Loop。镜头提示词重新生成仍使用该流程。普通讨论不进入质量检查，不新增图片／视频能力或检查 UI。

## 当前代码维护：兼容写法与编码风格

1. 使用满足当前需求的简单实现；在界面、领域、网络、存储和状态生命周期边界抽象，不为假设需求建立框架或隐式注册机制。
2. 变量表达具体业务对象；函数使用动词与业务对象；类表达明确职责；文件按业务功能命名。子任务有独立业务含义、需要复用或职责混杂时才拆分，避免机械拆分和多层转发。
3. 函数按必要校验、业务处理、返回结果组织。外部数据在进入业务前验证，内部调用遵循类型契约，不重复防御性兜底。
4. 参数和返回值写明类型；共享复杂结构使用明确契约。阶段不同的 JSON 内容通过 JsonObject 表达，并由对应阶段校验器检查，不能用该类型逃避必要的边界校验。
5. 明确单位与缺失语义：时间轴和时长为毫秒整数，原文坐标为 Unicode 码点，未指定目标使用 None，不用空字典或零值掩盖失败。
6. 当前层没有明确处理职责就让异常传播；只为恢复、维护失败状态、必要的接口转换或任务边界反馈而捕获。优先具体异常，原样重抛用裸 raise，转换用 raise NewError(...) from exc；任务边界记录完整错误，界面显示类型和消息。配置缺失首次使用明确报错，程序错误不重试、不返回默认结果。媒体提交、查询和下载的重试边界见接口设计第 10 节。
7. 保持入口、实际实现和中间结果可查；记录必要失败上下文，避免重复日志。网络替换通过显式 transport，文件与模型边界可独立验证。

仓库 ruff.toml 只覆盖当前短视频领域、界面和文字评估入口，检查名称／导入及函数类型标注，统一100字符排版。Ruff仅作为开发检查工具，不加入运行依赖；可运行 ruff check 和 ruff format --check。

## 模型配置、对话与编辑

短视频顶部和项目设置均复用第一部分 ModelConfigDialog；两部分共享服务商、地址、密钥与模型，运行中禁用配置切换。普通聊天只提供建议，不恢复作用目标、应用修改、聊天修订或另存候选。稿件与提示词直接编辑保存；仅文案与分镜支持历史恢复。人物／场景／道具及镜头提示词按对象与状态保留当前一份，替换时清理旧记录和中间候选，取消提示词旧来源提示及确认。打开项目的恢复步骤清理已有非当前提示词，普通读取保持只读。

聊天入口统一使用 ConversationStore 和 build_conversation_context。ConversationService 中重复的文件读写与上下文拼接已删除；界面和评估入口直接访问 service.store。长历史按完整轮次裁剪副本，本轮消息只加入一次。预检失败不落盘，执行时保存用户消息与最终回复，停止和恢复沿用明确终态。详见[会话管理](conversation_management.md)。
